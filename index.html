A private OpenStack cloud for DisasterAid, built on laptops

DisasterAid is a disaster-response and volunteering platform built by Team ANEMOS at ESPRIT. This page is about the part nobody sees: the cloud we built from scratch to run it, what broke along the way, and what I would do differently.

Stack OpenStack (Ubuntu 24.04, Flamingo), Heat, Kubernetes Automation Ansible, GitLab CI Hardware 7 laptops running VMs Team Team ANEMOS, ESPRIT

The big picture

One controller runs the OpenStack control plane. Compute nodes run the VMs. The VMs sit on a private network behind a virtual router and reach the outside world through floating IPs. From commit to running pods

Nothing was clicked together by hand more than once. A change moves through the same five stops every time.

GitLabHolds the code and runs the CI pipeline on every push.
AnsibleConfigures every node the same way, so rebuilds match.
HeatA stack template creates the cluster’s VMs, ports and security groups.
KubernetesRuns the application containers across the cluster.
DisasterAidAngular, Spring Boot and PostgreSQL with PostGIS.

Why these tools together: Heat answers “what machines and networks exist”, Ansible answers “how is each machine configured”, and Kubernetes answers “what runs on them”. Keeping those questions in separate tools meant a broken laptop meant a rebuild, not a rescue.

What broke and how I fixed it

Neutron agents would not start

Symptom: the Linux bridge, DHCP and L3 agents failed while neutron-server was installed.

Cause: the agent package version did not match neutron-server, a side effect of mixing package sources.

Fix: I moved the data plane to Open vSwitch, started the missing neutron-rpc-server, and confirmed every agent was alive in openstack network agent list.

Glance answered, but not for the client

Symptom: openstack image list failed while glance-api was running.

Debugging: I took a token with openstack token issue, called the API with curl, checked the port with ss, and restarted glance-api and Apache after each config change.

Result: after the database sync and a config correction, an image upload and list worked.

Nova service creation and compute discovery

Symptom: the CLI rejected creating the compute service (HTTP 400), and new compute nodes did not appear.

Fix: I created the service through the Python SDK, ran the cell and database syncs, then used cell discovery so each compute node registered as a hypervisor.

Laptops on different networks

Symptom: the machines were not on one LAN while we built the cluster.

Fix: I joined the nodes over a Tailscale VPN first, then moved MariaDB and etcd to LAN addresses once everyone shared a network, with chrony keeping time consistent.

The automation, reconstructed

I reset the environment after the project, so the original templates and playbooks are gone. The sketches below show how the automation was structured, rewritten from how these tools work. They are illustrative, not copies of the originals.

Heat: the cluster as one stack

heat_template_version: 2021-04-16
parameters:
  key_name: {type: string}
  network: {type: string}
  image: {type: string, default: ubuntu-24.04}
  flavor: {type: string, default: m1.medium}
resources:
  k8s_sg:
    type: OS::Neutron::SecurityGroup
    properties:
      rules:
        - {protocol: tcp, port_range_min: 22, port_range_max: 22}
        - {protocol: tcp, port_range_min: 6443, port_range_max: 6443}
  control_plane:
    type: OS::Nova::Server
    properties:
      image: {get_param: image}
      flavor: {get_param: flavor}
      key_name: {get_param: key_name}
      networks: [{network: {get_param: network}}]
      security_groups: [{get_resource: k8s_sg}]
  workers:
    type: OS::Heat::ResourceGroup
    properties:
      count: 2
      resource_def:
        type: OS::Nova::Server
        properties:
          image: {get_param: image}
          flavor: {get_param: flavor}
          key_name: {get_param: key_name}
          networks: [{network: {get_param: network}}]
          security_groups: [{get_resource: k8s_sg}]

Ansible: one playbook, three roles of machine

- hosts: k8s
  become: true
  roles:
    - common      # chrony, swap off, kernel modules, sysctl
    - containerd  # SystemdCgroup = true
    - kubernetes  # kubeadm, kubelet, kubectl at a pinned version
- hosts: control_plane
  roles: [kubeadm_init, cni]
- hosts: workers
  roles: [kubeadm_join]

GitLab CI: lint first, deploy on demand

stages: [lint, deploy]
lint:
  stage: lint
  script: [yamllint ., ansible-lint]
deploy:
  stage: deploy
  when: manual
  script:
    - openstack stack create -t cluster.yaml --wait k8s
    - ansible-playbook -i inventory site.yml

Credentials live in GitLab CI variables, never in the repository.

Where this stack tends to fail, and how I check

These are the known trouble spots for this combination of tools, and what I would look at first.

  • A Heat stack ends in CREATE_FAILED. Usually a flavor too big for a laptop, a missing image or no free floating IPs. openstack stack failure list names the failing resource.
  • Kubernetes nodes stay NotReady. Typical causes are swap still on, a container runtime cgroup driver that differs from the kubelet’s, or no CNI installed. kubectl describe node and journalctl -u kubelet show which.
  • A node cannot join. The join token expires after 24 hours, and clock drift between nodes breaks certificates, which is why chrony runs everywhere.
  • Pods cannot talk across VMs. The tenant network MTU here is 1450 because of the overlay, so a CNI that wraps packets again needs a lower MTU.
  • Ansible changes things on every run. Raw shell tasks are not idempotent, so I use modules and changed_when, and a second run should report zero changes.
  • The CI runner cannot reach the nodes. Check the security group for port 22 and that the runner sits on a network that can route to the floating IPs.

Limits, and what I would change

  • One controller is a single point of failure. I would run three controllers with a Galera database cluster, clustered RabbitMQ and a virtual IP.
  • Swift has two devices on one host. Replication survives a disk failing, not a machine. A production ring needs several nodes.
  • Internal endpoints use plain HTTP. I would add TLS and move credentials into a secrets store, with GitLab CI variables for pipeline secrets.
  • Provisioning is only partly declarative. The control plane was installed by hand. I would capture it in Ansible roles so a rebuild is one command.
