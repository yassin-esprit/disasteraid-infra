DisasterAid’s private cloud: built, automated and watched

DisasterAid is a disaster-response and volunteering platform built by Team ANEMOS at ESPRIT. This page explains the cloud underneath it, from a simple tour for anyone to the engineering details: how it was built on seven laptops, how GitLab automates it, how it is monitored, and what broke along the way.

Load balancing: the receptionist

Imagine a restaurant with one host and three waiters. Without a host, every guest runs to the first waiter and he drowns. With a host, guests are shared out evenly. In OpenStack, the host is a service called Octavia. It sits in front of several copies of an app, shares the visitors between them, and keeps checking that each copy is still alive. In DisasterAid’s cloud, Octavia was installed and running on the controller. The game below uses simulated traffic to show the idea.

Automation: from commit to running app

Nothing was built by clicking around more than once. A change travels down an assembly line: it is checked, the machines are created, they are configured, and the app starts. A token moves along the line below, lighting up each stage.

In plain words: Think of a factory conveyor belt. You put a change on the belt at one end. Machines inspect it, build the servers, set them up and start the app. If the inspection fails, the belt stops before anything breaks.
StageWhat it doesWhy it exists
Checkyamllint and ansible-lint on the templates and playbooks.Catches typos before they touch a server.
Build VMsThe Heat template creates the control-plane VM, the workers and the security group.Infrastructure is described in a file, so a rebuild matches the original.
ConfigureAnsible installs containerd and kubeadm, then runs init and join.Every node ends up configured identically.
Run appKubernetes starts the Angular, Spring Boot and PostgreSQL/PostGIS containers.The cluster keeps the app running and restarts failed containers.

Why three tools: Heat answers “what machines and networks exist”, Ansible answers “how is each machine configured”, and Kubernetes answers “what runs on them”. Keeping these questions separate means a broken laptop is a rebuild, not a rescue.

Monitoring: watching the cloud

A cloud you cannot see is a cloud you cannot fix. Each machine runs a small helper that reports its health. Prometheus visits every helper on a schedule and stores the numbers, and Grafana turns them into charts.

In plain words: Monitoring is a nurse doing rounds. Every 15 seconds the nurse (Prometheus) checks each patient (laptop), writes down temperature and heartbeat, and a wall screen (Grafana) shows the trends, so you spot a problem before anyone complains.

Illustrative configuration (reconstructed, like the other sketches):

scrape_configs:
  - job_name: node
    scrape_interval: 15s
    static_configs:
      - targets: ['controller:9100', 'compute1:9100', 'compute2:9100', 'compute3:9100']
# CPU used, per machine, in percent
100 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100

Typical dashboard panels for this kind of cloud are CPU, memory, disk and network per node, plus an up/down panel per service. What I would add next: Alertmanager, so a crashed service sends a message instead of waiting for someone to look, and an OpenStack exporter for API health.

Ansible: one playbook, three roles of machine

- hosts: k8s
  become: true
  roles:
    - common      # chrony, swap off, kernel modules, sysctl
    - containerd  # SystemdCgroup = true
    - kubernetes  # kubeadm, kubelet, kubectl at a pinned version
- hosts: control_plane
  roles: [kubeadm_init, cni]
- hosts: workers
  roles: [kubeadm_join]

Where this stack tends to fail, and how I check

These are the known trouble spots for this combination of tools, and what I would look at first.

  • A Heat stack ends in CREATE_FAILED. Usually a flavor too big for a laptop, a missing image or no free floating IPs. openstack stack failure list names the failing resource.
  • Kubernetes nodes stay NotReady. Typical causes are swap still on, a container runtime cgroup driver that differs from the kubelet’s, or no CNI installed. kubectl describe node and journalctl -u kubelet show which.
  • A node cannot join. The join token expires after 24 hours, and clock drift between nodes breaks certificates, which is why chrony runs everywhere.
  • Pods cannot talk across VMs. The tenant network MTU here is 1450 because of the overlay, so a CNI that wraps packets again needs a lower MTU.
  • Ansible changes things on every run. Raw shell tasks are not idempotent, so I use modules and changed_when, and a second run should report zero changes.
  • The CI runner cannot reach the nodes. Check the security group for port 22 and that the runner sits on a network that can route to the floating IPs.

What broke and how I fixed it

In plain words: Things rarely work the first time. Here are the real problems from the build and how each one was solved.

Neutron agents would not start

Symptom: the Linux bridge, DHCP and L3 agents failed while neutron-server was installed.

Cause: the agent package version did not match neutron-server, a side effect of mixing package sources.

Fix: I moved the data plane to Open vSwitch, started the missing neutron-rpc-server, and confirmed every agent was alive in openstack network agent list.

Glance answered, but not for the client

Symptom: openstack image list failed while glance-api was running.

Debugging: I took a token with openstack token issue, called the API with curl, checked the port with ss, and restarted glance-api and Apache after each config change.

Result: after the database sync and a config correction, an image upload and list worked.

Nova service creation and compute discovery

Symptom: the CLI rejected creating the compute service (HTTP 400), and new compute nodes did not appear.

Fix: I created the service through the Python SDK, ran the cell and database syncs, then used cell discovery so each compute node registered as a hypervisor.

Laptops on different networks

Symptom: the machines were not on one LAN while we built the cluster.

Fix: I joined the nodes over a Tailscale VPN first, then moved MariaDB and etcd to LAN addresses once everyone shared a network, with chrony keeping time consistent.

Limits, and what I would change

  • One controller is a single point of failure. I would run three controllers with a Galera database cluster, clustered RabbitMQ and a virtual IP.
  • Swift has two devices on one host. Replication survives a disk failing, not a machine. A production ring needs several nodes.
  • Internal endpoints use plain HTTP. I would add TLS and move credentials into a secrets store, with GitLab CI variables for pipeline secrets.
  • Provisioning is only partly declarative. The control plane was installed by hand. I would capture it in Ansible roles so a rebuild is one command.
